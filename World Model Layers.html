World Model Layers

Singularity Flow builds three related pictures of a repository. Each answers a different question. All three are built without a language model; a model, where one is allowed at all, only phrases facts that were already extracted and checked.

AST intelligence

What is declared, and what does each call reach?

Code facts at three levels of certainty: text, syntax and semantic. Compilers and type checkers resolve calls and overrides.

Registered World Model (v4)

What should an agent know for this phase?

Sixteen deterministic extractors turn source into cited facts. Four fixed views are composed from them and published to a state branch.

Repository knowledge (L0–L5)

How does this code work, in plain terms?

A newcomer's explanation sorted into six levels, from inventory to change risk. Every observed item cites a file and line range.

Guidance, never authority

A missing, stale or failed model is left out with a recorded reason and a warning. Nothing blocks, refuses or approves work because of it.

Deterministic first

Every layer builds with no model. A model may only arrange or phrase facts that already exist; it cannot add one.

Evidence on every claim

A World Model fact carries its evidence ID, source path and content hash. A knowledge item carries a file, a line range and a hash of those lines.

Repository code never runs

No build tool, package manager, test, annotation processor or Python interpreter is started to extract anything.

Part 1

AST intelligence

The AST layer answers structural questions about code at a declared level of certainty, called assurance. A fact never claims more assurance than the tool that produced it can give. Results are content-addressed and cached under the repository's Git directory, so a second read of unchanged files is nearly free.

The three assurance levels

AssuranceProduced byWhat it can say
textBuilt-in lexical facts for all languages. The polyglot structural preview (sflow-polyglot-syntax) for Java, Python, Kotlin and Swift.Declarations, signatures, nesting, imports, annotations and declared relationships, each with an exact span. The preview scans lines; it does not parse. It cannot satisfy a syntax gate.
syntaxsflow-typescript-syntax: the parser of the TypeScript compiler bundled with Singularity Flow.Declarations, imports and inheritance for .js .jsx .mjs .cjs .ts .tsx, with signatures that stop before the body.

How semantic facts are extracted

  1. Warm-up binds the project. wm ast warm --semantic --provider PACK --project KIND:ROOT --profile default shows a plan, asks for an exact confirmation phrase, then records the toolchain's identity and the hashes of the project's build files. Nothing semantic runs before this. A file uses the innermost warmed project that contains it, so a parent pom.xml warmed once covers its modules.
  2. A stable skeleton comes first. Semantic facts never invent identities. For JS/TS the syntax and semantic packs share one ID scheme. For Java and Python the compiler names each end of an edge by path, name and the line of that name, and the pack joins that to the preview's declaration ID. An end the preview does not have contributes no edge. On Spring Framework's sources 99.9% of the compiler's answers join.
  3. Calls are a graph, not a list of call sites. One edge per caller and callee, at the first call. Method calls, new or constructor calls and method references count; calls inside lambdas belong to the enclosing method.
  4. Overrides record dependency injection. A call through an interface names the declared method, because the compiler cannot know what gets injected at run time. Java reports every repository method a method overrides, through any supertype. Python resolves each base class with go-to-definition and pairs same-named methods (dunder methods are left out).
  5. Work is bounded. Adapter requests carry at most 200 files and 1 MiB for syntax, 500 files and 2 MiB for semantic packs, with a 2 MiB response budget and a 30-second timeout. A response over budget is split in half and retried, so only a single oversized file can degrade.

Part 2

Registered World Model (v4)

The registered World Model is what phases receive as grounding. It belongs to the repository's source, not to any Story: it is built from an exact snapshot, published to a state branch, and read by every Story that wants it. The build is a fixed pipeline of nine stages.

  1. Scope and source snapshot

    Purpose. Decide exactly which bytes the model describes.

    • The scope manifest takes worldModel.sourceRoots (everything when unset) and sharedRoots, and always excludes .git, Singularity Flow's own state, singularity/, .github/agents, the Story work-item root and your excludedRoots. Exclusions always win and are matched case-insensitively.
    • In-scope paths must be clean, or the build stops with WMB_SOURCE_SNAPSHOT_REQUIRED. The revision is the last commit that touched in-scope paths, and the snapshot hash covers the scoped file list (path, mode, content hash). Story and metadata commits therefore do not make the model stale.
    • A sealed request and plan bind the source, scope, view and extractor registries, consumer profile, output budget and cache policy. Planning changes nothing.

  2. Extraction

    Purpose. Turn source into typed, cited facts. Fifteen extractors run in every build and required-fact-coverage is appended last; a seventeenth, legacy-migration-resolution, runs only inside wm migrate. "Ledger only" facts are in the fact ledger (queryable with wm facts, and imports feed the CALM projection) but in none of the four views' type lists. Every extractor is a deterministic module declared with network: none, model: never and writes: derived-store-only, and has a reviewed conformance fixture suite. Its identity includes a hash of the World Model kernel's source, so any change to the kernel is a visible registry change.

  3. Facts, evidence and derivations

    Purpose. Make every claim checkable later. Each piece of evidence (EV-) names a path in the pinned snapshot and its content hash. Each extractor run is a derivation (DRV-) that binds the extractor version, its implementation hash and its inputs. Each fact (FACT-) is named by a hash of its type, subject, claim, status, assurance and evidence.

    An unavailable fact has no claim and a typed reason such as NO_REGISTERED_PRODUCER or NO_RUNTIME_EVIDENCE, so "we could not find out" is never confused with "it does not exist".

  4. Per-view selection and admission

    Purpose. Give each view exactly the facts it needs, inside its budget. Each view declares required, optional and required-unavailable fact types. Selection takes one anchor fact per required type and every contradicted fact, then fills the remaining slots round-robin by type up to the view's fact limit. Stale facts are never eligible.

    The admitted facts are the subset that still fits the view's output budget (1,400 tokens) and the composer's input limit (8,000 tokens). Every fact left out is recorded with the reason output-budget or input-budget.

  5. The four registered views

    ViewPurposeRequired factsSections
    arch.contracts@4The repository's public contracts and who implements and consumes theminterface, implementation, consumer-dependency, protocol-field, schema-contract, signature; runtime-guarantee as unavailablepublic contracts · implementations · consumers
    biz.rules@4Registered rules, their conditions and where they liverule-definition; business-meaning as unavailable until a person confirms itregistered rules · conditions and outcomes · rule locations
    dev.hotspots@4Where structure, change and dependencies concentratechange-frequency, dependency-degreestructural · change · dependency concentration

    All four views forbid reading source bodies and referring to other views. Facts are placed in the section that names their type.

  6. Composition

    Purpose. Turn admitted facts into a readable Markdown view.

    • Deterministic (default). A renderer writes each admitted fact as its canonical sentence followed by one sorted citation group, such as [F:FACT-…], in the section for its type. Its output is reproducible byte for byte.
    • Model-required. A governed model call with no tools receives a pinned prompt: the rules, the citation grammar, the candidate JSON schema, the view contract, the consumer profile, the budget, the scope and the admitted fact packet. It must narrate every admitted fact with its exact canonical claim and may not add facts, IDs, paths or metadata.
    • Model-optional currently always routes to the deterministic renderer for the four built-in views.

  7. Validation

    Purpose. Prove the candidate says only what the facts say. Twenty-two deterministic checks run on every candidate:

    • Shape: JSON, schema, view identity, registered title, required sections, section order, no unregistered sections, word budgets, total output.
    • Faithfulness: each factual unit is exactly the canonical sentences plus one citation group; no unknown or invented IDs; every path- or symbol-like token is registered and admitted; the model route cites every admitted fact.
    • No strengthening: an unavailable fact cannot become "does not exist", a partial one cannot become "all" or "complete", and assurance can never be upgraded.
    • Boundaries: required and required-unavailable facts present, contradictions surfaced, scope respected, no source-body access, no cross-view references, kernel metadata intact.

    On the model route, one narrow layout repair is allowed: citation groups split across sentences may be merged when every cited fact is admitted and the text is exactly the canonical sentences. The full validator then runs again.

  8. Materialization, cache and publication

    • After validation the kernel adds a header of hashes, a canonical JSON facts block and a stamp (source commit, view hash, prompt hash, execution unit, model, and assurance: validated-derived-view).
    • The cache key combines 12 identities: source, scope, view version and contract, fact ledger, consumer profile, composer, schema, validator, budget and execution profile. Under reuse-valid a cache hit is revalidated before it is reused.
    • Publication replaces singularity/world-model/ in one compare-and-swap commit on the state branch; application branches are untouched. A recovery marker is written first, so a failed push resumes with wm recovery publish and no new extraction or model call.
    • At Story creation each phase's views are pinned to exact history for that Story. A miss records an unavailable pin; Story start never builds anything.

  9. Consumption by phases

    • A phase gets the views assigned to it, falling back to its agent's views. It receives the pinned packet when the pin can be re-proved; otherwise the current published projection; otherwise nothing, with a reason code.
    • The World Model section is optional in the prompt budget. If it does not fit it is dropped whole and recorded as WMP_GROUNDING_OMITTED_BY_BUDGET.
    • Grounding is off or warn; an old enforce setting acts as warn. A stale model warns; it never blocks.
    • A CALM architecture projection (arch.calm@1) is built from import, interface and schema facts without a model and validated with the CALM CLI. A Story's architecture intent is checked against it and only ever warns.

Part 3

Repository knowledge (L0–L5)

Repository knowledge (wm knowledge) explains how the code works to someone new to it, including a product owner. Each level answers one question. A level is ready, thin or insufficient, and each status comes with its reason.

Inputs

  • The committed tree at HEAD, never working files. Code under worldModel.sourceRoots, excluding build output, generated files and Singularity Flow's own state. Limits: 4,000 code files, 512 KB per file, 48 MB in total. A larger repository is split into areas you choose with --area.
  • Git history: up to 2,000 non-merge commits from the last 12 months, for change counts and co-change.
  • Approved requirements: approved Markdown phase artifacts whose bytes still match their approval hash. Uploaded documents, Jira text and drafts are not read.
  • Compiler-resolved calls from the AST layer, once a semantic pack is warmed.

The engine

Files are grouped into areas of about 150 files. An analysis engine reads each area as text: a regex outline of declarations with extents from braces or indentation, then four lenses. Concepts classify modules into layers and score domain words. Entities find data shapes. Flow finds entry points, calls and effects. Logic builds each function's decision tree. Framework producers add what the engine does not know: build commands, routes, data classes, HTTP clients, configuration keys and test cases. No language service and no model is involved.

The call graph

Calls drive L2, journeys, test coverage and impact, so their accuracy matters most.

  • By name, without a warmed pack: a call is linked only when exactly one repository function of that name fits the receiver. The edge is labelled by-name.
  • Resolved, with a warmed pack: compiler answers replace a file's name matches. A call to an interface or base method also reaches every override, marked via: override. This is how a Spring or Micronaut controller's call to an injected OrderService reaches OrderServiceImpl, and a FastAPI route reaches each implementation of an abstract service.
  • Metrics report callsResolved, callsMatchedByName and which packs resolved them.

Citations, review and prompts

  • Citations. Every observed item cites a path, a line range and a hash of those exact lines; building one without a citation fails. Derived items (concepts, hotspots, co-change, impact) may have none. Item IDs are stable across builds, and invalidCitations re-hashes every citation.
  • Human review. wm knowledge confirm|correct|reject writes to docs/knowledge/confirmations.yml, which is committed with the code. A review is bound to the hash of the lines it cites, so it goes stale when the code moves and asks to be reviewed again.
  • Prompt slice. With worldModel.knowledge.prompt: slice, a phase prompt gets the items related to the Story's title, description and acceptance criteria, in a role-specific section order, within maxBytes (8 KiB by default). Composing it never calls a model.
  • Benchmarks. Four fixture repositories (React shop, Spring orders, Android notes, FastAPI orders) list the items a reviewer expects. Tests require at least 90% recall on the shop and 100% on the others.

Part 4

In the workflow

The World Model is built once per source change and read by every Story. Each phase asks for the views that match its job, at a depth that fits it, and gets a role-specific slice of repository knowledge beside them.

How it is wired

  1. Configure

    worldModel.views lists the enabled views (all four in the packaged workflow). Each phase sets worldModel: {views, depth}. Each agent's Markdown names its own views in sflow-world-model-views; a phase without views falls back to its agent's, or both are combined when worldModel.agentViews is union.

  2. Build and publish

    The packaged setting is materialization.mode: explicit with confirmation: prompt: someone runs sflow wm plan then sflow wm build, reviews the plan and confirms it. The views are published to the state branch for every Story to share. Repository knowledge builds on demand and caches per commit; semantic packs are warmed once per project.

  3. Story start pins history

    When a Story is created, each phase's views are pinned to the exact published history for that Story, so a later rebuild cannot change what an in-flight Story was grounded on. If nothing is published yet, the pin is recorded as unavailable and the Story starts anyway.

  4. Each phase prompt

    When a phase prompt is composed (sflow next, the /sf-* skills, or wm compose), it gets the pinned view packet when the pin can be re-proved, otherwise the current published views, otherwise nothing with a recorded reason. Repository knowledge adds an 8 KiB slice focused on the Story's title, description and acceptance criteria, ordered for the phase's reader: product for intake and specification, architect for design and planning, tester for verification and conformance, developer otherwise. Both sections are optional in the prompt budget and dropped whole if they do not fit.

  5. Checks that only warn

    Grounding verification, staleness and the architecture-intent check against the CALM projection report warnings in receipts. None of them stops, refuses or approves a phase.

Benefits across the whole lifecycle

  • Grounded instead of guessed. Agents start from cited facts about the actual code rather than from what a model assumes a typical repository looks like.
  • Small and predictable context. A view is capped at 1,400 output tokens and the knowledge slice at 8 KiB by default, far less than reading the files the facts came from.
  • The same picture for every agent and phase. One published build on the state branch, pinned per Story, so the product owner's intake and the tester's verification describe the same code.
  • Auditable. Every sentence traces to a fact ID or a file and line range, and prompt receipts record which views and which slice a phase received.
  • Cheap and offline. Building needs no model and no network; deterministic views and knowledge are reproducible and cached.
  • Never in the way. A missing, stale or dropped section is a warning, so a repository without a World Model runs its whole lifecycle.
Where the benefit is smaller today
  • dev.impact describes the latest committed change in scope relative to its parent, and its dependency edges are lexical. A Story's own in-progress diff and compiler-resolved calls reach the agent through repository knowledge, not through this view.
  • dev.hotspots is mostly typed "unavailable" facts, so the one phase that asks for it gets little from it.
  • The evidence: true flag on verification phases is recorded in the grounding plan but does not change which facts the current view path delivers.
Part 5

With and without models

A model appears in exactly two places, and both are optional. Everywhere else a model is forbidden by design: the World Model extractors declare model: never, and the AST packs, the knowledge build, prompt slices and the CALM projection contain no model call.

The model's role

In both places the model works only as a writer of facts that already exist. Extraction, selection, citation and validation decide what is true. A failed or missing model removes prose; it never removes facts and never blocks a phase. The model that runs a Story phase is a consumer of these layers, never a producer of them.

Part 6

Gaps and next steps

These come from reading the code, not from the documentation. Items marked unverified were inferred from the code and not reproduced.

Thin coverage in the World Model views

  • dev.hotspots is mostly "unavailable". No extractor produces change-frequency, dependency-degree, complexity-metric or incident-mapping, so the view reports typed unavailable facts; only CODEOWNERS concentration is real data. Repository knowledge already computes churn, complexity and importers for its L5 hotspots, and that logic could feed this view.
  • World Model call edges are lexical. call-reference-edge finds same-file candidates and marks them partial. The compiler-resolved calls and overrides from the AST packs reach repository knowledge but not dev.impact. Feeding them in is the largest accuracy gain available.
  • Runtime and contradiction facts need input. Runtime guarantees and frequencies come only from an observations file you supply, and no extractor produces contradicted facts yet, so the contradiction checks have nothing to work on.
  • model-optional never uses a model for the four built-in views; it behaves like deterministic.

Repository knowledge

  • Logic is built for at most 240 functions per area, test files included, so a large area can lose rules for its later functions (unverified).
  • Four declared item kinds are never produced: module-dependency, call, test-coverage and interface. Their content lives in the graph and in relations instead.
  • A build merged from several areas drops the resolved-call metrics from its summary.

Documentation that lags the code

  • The builder doc mentions 20 validation checks; the code has 22.
  • worldModel.v4.depth is read by the builder but rejected by configuration validation, so depth comes only from --depth, the phase or materialization.depth.
  • A phase built at deep may be compared against a standard identity and reported stale (unverified).
  • Setting worldModel.allowedSubjects may reject the coverage and human-confirmed facts, whose subject kinds it does not allow (unverified).
  • The knowledge benchmark table lists 20 expected items for Android notes and 17 for FastAPI orders; the fixture files hold 17 and 16.
Suggested order
  • Feed AST calls and overrides into the World Model as dependency-edge facts, so dev.impact sees resolved calls and injected implementations.
  • Produce change-frequency and dependency-degree facts from Git history and the import graph, so dev.hotspots carries data.
  • Fix the documentation drift and test the two unverified configuration paths.
